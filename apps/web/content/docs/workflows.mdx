Rules decide what happens to a conversation without anyone touching it: who answers outside business hours, which queue a new conversation goes to, who gets it, what happens when nobody replies, and when it closes. They are a small, declared set of five types, stored in `sendo_rules` per tenant (optionally per number), and admins edit them on the **Reglas** screen without a deploy.

## Rule types [#types]

| Type             | Params                                                                                                                                                                                | Runs                                                          |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `business_hours` | `timezone` (IANA), `schedule` (`mon`…`sun`, each a list of `["HH:MM", "HH:MM"]` ranges, end exclusive, `24:00` = midnight), `holidays?` (`YYYY-MM-DD`), `outsideMessage`, `appliesTo` | On every inbound message and on the tick                      |
| `route`          | `match: { channel?, account?, source?, keywords? }`, `action: { queue?, tags?, to: "agent" \| "human", reason? }`                                                                     | On a new or reopened conversation; in order, first match wins |
| `auto_assign`    | `queue?` (omitted = any queue, `null` = no queue), `strategy: "least_open" \| "round_robin"`                                                                                          | When a conversation enters `human`, inside hours              |
| `escalate`       | `afterMinutes` (1–10 080, open minutes only), `queue?`, `action: "reassign" \| "notify" \| "return_to_agent"`                                                                         | On the tick                                                   |
| `auto_close`     | `afterDays` (1–365) without activity                                                                                                                                                  | On the tick                                                   |

- **Business hours.** Outside hours the after-hours message is sent at most once per conversation per closed period, and only while the 24-hour window is open (it isn't a template; otherwise it's logged). Escalation and auto-assign timers don't count closed time. With `appliesTo: "human"` the AI keeps answering and the message goes to conversations with a person; with `"all"` the AI is held too. A rule for one number wins over the tenant-wide one.
- **Routing.** Keywords match whole words in the first message, ignoring case and accents. `source` is the `[#code]` of a link (or `ad:<id>` for a Click-to-WhatsApp ad, see [Links](/docs/widgets#attribution)). The action sets the queue, adds tags (created in gray when missing) and hands off to a person with `by: "rule:<key>"` when `to: "human"`. No match keeps today's behaviour.
- **Every rule action is visible.** It adds a system line to the thread («Asignada a Ana por la regla Turno cobranza») and emits `conversation.status`, `conversation.assigned` or `rule.applied` with `by: "rule:<key>"`; `notify` emits `escalation { conversation, rule, minutesWaiting }` for your app to turn into a notification.

A rule's `key` is its name: unique per tenant, quoted in those system lines, and what `rules sync` upserts by. Every `params` object is validated by the zod schemas exported from `@quami/sendo` (`ruleParamsSchemas`, `parseRuleParams`); a stored rule that fails them is ignored by the engine and shown as an error on the screen.

## Roles and permissions [#roles]

`resolveRole` decides who can do what ([Team inbox](/docs/team-inbox#roles)). Rules are admin only (`rules.manage`): `sendo.rules.*` throws `FORBIDDEN` for other roles, and the screen shows "No tienes acceso a Reglas".

| Capability                                                                    | Agent | Supervisor | Admin |
| ----------------------------------------------------------------------------- | ----- | ---------- | ----- |
| See conversations assigned to self, plus unassigned ones in own queues        | ✓     | ✓          | ✓     |
| See all conversations in the tenant                                           |       | ✓          | ✓     |
| Reply, step in, note, tag, approve drafts on visible conversations            | ✓     | ✓          | ✓     |
| Take an unassigned conversation, return it to the AI, close it                | ✓     | ✓          | ✓     |
| Reassign to someone else; pause the AI on a conversation                      |       | ✓          | ✓     |
| Reports and metrics                                                           |       | ✓          | ✓     |
| Numbers, rules, AI pause per number, tenant snippets, tag catalog, broadcasts |       |            | ✓     |

The package checks are the source of truth for every adapter; Supabase RLS mirrors them as defense in depth.

## Rules in code [#code]

Declare the rules your app ships with in a standalone module, so the CLI can load it without Next.js:

<Sample file="workflows.ts" region="code" title="lib/sendo-rules.ts" />

Then store them for a tenant:

```shell
npx @quami/sendo rules sync --config lib/sendo-rules.ts --tenant <uuid>
```

- Missing rules are inserted by `(tenant, key)` with origin `code`. Rules already there (for example, edited on the screen) are **never overwritten** unless you pass `--force`, which replaces type, params and number but keeps position and on/off.
- Every rule is validated first; one invalid rule exits 1 and nothing is written.
- The engine reads stored rules only, so run the sync after changing the file (for example, in your deploy step). Full flags in [CLI](/docs/cli#rules-sync).

## The Reglas screen [#screen]

```shell
npx shadcn add @sendo/workflows
```

It adds the screen at `/inbox/rules` (`app/(protected)/inbox/rules`) and the tick route. Admins:

- see the rules in evaluation order, each with its type, number, a one-line summary and who edited it last; **Desde código** marks rules from `rules sync`;
- turn rules on and off, move them up and down (route rules are first-match-wins), and delete them (a code rule comes back on the next sync);
- create rules of the five types and edit them with a typed form per type: the business-hours editor has the time zone, a weekly schedule with several ranges per day, holidays, the after-hours message and who it applies to. Forms validate with the package schemas before saving, and the server validates again;
- see an invalid stored rule as an error row with the problems listed, and fix it in the form.

Every change records `updated_by` (the actor's `userId`). Before using the screen, implement `requireUser()` in `app/(protected)/inbox/rules/rules-config.ts` (it throws until you do) and configure `resolveRole`. Optionally implement `resolveUserNames` there to show "Editada por Ana". Texts can be overridden with `<RulesScreen strings={{ ... }} />`.

## The tick [#tick]

`sendo.maintenance.tick()` runs, in order and within a 50-second budget: after-hours bookkeeping (conversations held outside hours go back to the agent at opening), escalations, auto-close, broadcast batches, a billing re-check for numbers without a payment method (hourly) and the event prune (daily). It takes the lock `tick` (120 s), so two overlapping calls never double-send: the second returns `{ skipped: true }`. Call it **every minute**.

<Sample file="workflows.ts" region="tick" title="ts" />

`workflows` ships the route `app/api/sendo/tick/route.ts`: `GET` or `POST`, `maxDuration = 60`, and `401` unless the request carries `Authorization: Bearer <SENDO_CRON_SECRET>` (Vercel's `CRON_SECRET` is accepted too). With no secret configured it always answers `401`. The response is the `TickReport` JSON.
